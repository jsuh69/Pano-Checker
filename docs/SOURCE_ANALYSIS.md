# Pano-Checker 소스 분석 및 후속 개발 가이드

> 이 문서는 v0.8.0 분석 당시의 기록입니다. 현재 v0.9 변경 사항은 [개발 가이드](V0.9_DEVELOPMENT.md)를 참고하세요.

분석일: 2026-10-20. 기준 커밋: `c825179`, 펌웨어 버전: `0.8.0`.
이 문서는 저장소 소스와 로컬 설치 라이브러리를 정적으로 분석한 결과다. 센서 정확도, 전류, 실제 버튼 반응 시간은 실기기로 검증해야 한다.

## 1. 프로젝트 구성

| 파일 | 역할 |
| --- | --- |
| `M5stickS3-motor-checker/M5stickS3-motor-checker.ino` | 전체 펌웨어. 설정 상수, 전역 상태, 배터리, 센서, FFT, 버튼, 화면, 절전 처리 |
| `README.md` | 기능, 배선, 조작법, Arduino IDE 빌드 안내 |
| `.gitattributes` | 플랫폼 간 줄바꿈 관리 |

별도 모듈, 자동 테스트, CI, 의존성 고정 파일은 없다. 네트워크 통신·서버·데이터 저장 기능도 없으며 Wi-Fi는 시작 시 꺼진다. 설정과 보정값은 RAM에만 있어 재시작하면 초기화된다.

## 2. 실행 흐름과 상태

`setup()` → 보드/충전 활성화 → 무선 비활성화 → CPU 80 MHz/화면 설정 → I2C/마이크/IMU 초기화 → HIGH 감도에 맞춰 마이크만 활성화.

`loop()`에서는 버튼 및 배터리 처리를 명목상 50 ms마다 실행하고, 센서 처리 → 절전 판단 → 화면 갱신을 500 ms마다 실행한다. 캘리브레이션 중 분석 간격은 1 ms로 바뀌지만 수집 시간과 마지막 `delay(50)` 때문에 실제 1 ms 주기는 아니다. 센서 처리는 같은 루프에서 실행되므로 버튼과 기능 타이머의 분리는 완전한 비동기 실행을 의미하지 않는다.

| 상태 | 변수 / 초기값 | 의미 |
| --- | --- | --- |
| 측정 모드 | `sCurrentMode = ModePano` | RPM / 자력 |
| 감도 | `sSensLevel = High` | LOW, MID, HIGH, VIB, AUTO |
| AUTO 센서 | `sAutoIsVib = false` | AUTO가 마이크인지 진동인지 구분 |
| 보정 진행 | `sIsCalibrating` 및 시간·합계·횟수 | RPM과 자력 보정이 같은 상태를 공유 |
| 절전 | `sDisplayBlanked`, `sReadySinceMs` | 무검출 20초 후 센서/화면 끄기 |
| 마지막 주파수 | `lastHz` | 검출이 끊겨도 화면 상단에 마지막 Hz 유지 |

BtnA는 RPM/자력 전환, RPM에서 BtnB를 짧게 누르면 LOW→MID→HIGH→VIB→LOW, 길게 누르면 현재 센서의 AUTO 보정이다. AUTO에서 짧게 누르면 LOW로 이동한다. 자력 모드에서는 BtnB를 누르는 즉시 기준선을 보정한다.

## 3. 센서와 신호 처리

### 마이크

- 핀: DATA 16, BCK 17, WS 15. 8 kHz, 1024 샘플, 프레임 길이 128 ms.
- DC 평균 제거 → Hamming 윈도 → FFT → 크기 스펙트럼.
- 400–600 Hz 안의 최대 피크를 선택하고 인접 3개 bin으로 포물선 보간한다. FFT bin 간격은 7.8125 Hz이며 보간이 물리적 분해능 자체를 늘리지는 않는다.
- 350–650 Hz에서 피크 ±1 bin을 제외한 크기의 중앙값으로 잡음 바닥을 구한다. `20*log10(peak/noise)`로 판정한다.
- 최소 크기 25,000, 기본 최대 크기 4,000,000. 주파수 추적 허용 차이 18 Hz, 추적값은 이전 70% + 신규 30%.

| 감도 | 최소 피크/잡음 비 | 연속 프레임 수 |
| --- | --- | --- |
| LOW | 12 dB | 4 |
| MID | 9 dB | 3 |
| HIGH | 6 dB | 2 |
| AUTO(마이크) | 8 dB | 3 |

LOW/MID/HIGH는 모두 같은 주파수 대역을 사용한다. RPM은 `Hz * 60`을 정수로 잘라 표시하므로 마이크 표시 범위는 대략 24,000–36,000 RPM이다. 회전당 검출 주기가 1회라는 가정이며 기종별 주기 수·고조파 보정은 없다.

### 진동

- `Wire1`: SDA 47, SCL 48, 400 kHz, 주소 `0x68` 고정.
- BMI270 레지스터 `0x7D`로 가속도 전원을, `0x40 = 0xAC`로 설정을 제어하며 `0x0C`부터 6바이트를 읽는다.
- 목표 625 µs 간격으로 512개 벡터 크기 `sqrt(ax²+ay²+az²)`를 수집한다. 목표 수집 시간은 약 320 ms지만 I2C·버튼 처리 등이 추가된다.
- 평균 제거와 512샘플 Hamming 적용 후 1024개로 zero padding한다. 수집 개수/경과 시간으로 추정한 샘플링 주파수를 사용한다.
- 150–750 Hz 탐색, 기본 최소 크기 5,000, 300 ms 연속 검출 조건. 500 ms 분석 간격에서는 통상 다음 유효 프레임에서 확정된다.
- 벡터 크기를 사용하므로 축별 신호와 스펙트럼이 달라질 수 있다. 실제 ODR, data-ready 동기화, 누락·중복 샘플 여부는 확인이 필요하다. Zero padding은 실제 관측 시간에 따른 분해능을 개선하지 않는다.

### AUTO 보정

RPM 센서의 피크를 약 1.5초 동안 평균내어 하한을 평균의 0.5배, 상한을 3배로 설정한다. 보정 후 AUTO로 전환된다. 주변 무신호를 학습하는 방식이라기보다 보정 당시 피크 크기를 기준으로 하는 방식이다. 마이크 SNR 기준은 보정하지 않는다. 따라서 보정 시 모터를 켜는지 등 사용 절차를 정의할 필요가 있다.

### 자력

- GPIO 1에서 ADC 32회 평균. 모드 진입 또는 BtnB로 약 1초간 주변 기준선을 평균낸다.
- 기준선 차이가 10 ADC 미만이면 0, 그 외 `abs(raw-baseline) * 0.872`를 Gauss로 계산한다.
- 이전 출력 75% + 신규 값 25%로 평활화한다. 표시값이 20 G를 넘으면 활동 상태로 취급한다.
- ADC가 기준선 이상이면 S, 미만이면 N으로 표시한다. 계수와 극성은 센서 모델·장착 방향에 종속된다. 센서 모델, 감도 근거, ADC 감쇠/해상도/비선형 보정은 소스에 명시되어 있지 않다.

## 4. 배터리·전원·화면

`BatteryManager`는 1초마다 배터리 잔량을 읽고 최근 3개 중앙값을 표시한다. USB 연결 상태는 VBUS ≥ 4200 mV 또는 충전 상태 핀으로 판단하며 3회 연속 같은 판단일 때 화면에 반영한다. 외부 전원 감지 중 10초마다 충전을 다시 활성화한다. 내부 이름 `isCharging()`은 실제 충전 전류가 아니라 외부 전원/충전 신호를 뜻한다.

화면은 스프라이트 전체를 다시 그리며 검출 중 500 ms, 대기 중 700 ms 간격을 요청한다. 실제 호출은 센서 처리 주기에 종속되므로 대기 갱신이 약 1초로 양자화될 수 있다. 강제 갱신도 다음 센서 처리 시점에 적용된다.

20초 무활동 시 화면 sleep, 마이크/IMU off, CPU 10 MHz를 요청한다. ESP32 deep sleep/light sleep 진입은 아니며 루프와 배터리 처리는 계속된다. 클록 설정 반환값은 확인하지 않는다. 버튼으로 CPU 80 MHz와 화면/센서를 복구한다. 센서를 끄므로 소리·진동으로 자동 기상하지 않는다. CPU를 낮추면 최고속 충전이 된다는 코드 주석은 측정으로 입증되지 않았다.

## 5. 후속 개발 전에 확인할 위험

아래는 코드 경로와 로컬 라이브러리 구현을 근거로 한 항목이다. 실기기에서의 발생 빈도와 영향은 별도 검증 대상이다.

| 우선순위 | 위치 | 분석과 권장 조치 |
| --- | --- | --- |
| 높음 | `processAudioAndFFT()`의 `M5.Mic.record()` 직후 | 녹음 완료 대기 없이 같은 버퍼를 읽는다. 로컬 M5Unified 0.2.25 구현은 버퍼 요청을 큐에 게시하고 반환하며 완료 후 읽도록 문서화되어 있다. 미완성/이전 프레임 분석 및 동시 읽기·쓰기 가능성. 완료 확인 상태 또는 이중 버퍼를 도입한다. |
| 높음 | `handleButtons()` / `startCalibration()` | 모드 전환 시 진행 중 보정을 취소하거나 종류별 상태를 분리하지 않는다. 자력 보정 중 RPM으로 돌아오면 ADC 누적값을 FFT 보정에 섞거나 AUTO로 변경할 수 있다. 전환 시 보정 취소 및 누적값 초기화가 필요하다. |
| 높음 | 진동 수집 루프의 `handleButtons()` | 수집 중 모드/감도/센서 전원이 바뀌어도 로컬 `useVib`를 유지하며 이전 작업을 계속한다. 전환을 예약하거나 세대 번호 확인 후 프레임을 폐기한다. |
| 중간 | 함수 내부 정적 추적 변수 | 마이크 연속 프레임과 진동 연속 시작 시간이 모드 전환·절전·보정·일부 수집 실패에서 초기화되지 않는다. 재진입 시 과거 검출을 이어받을 수 있어 공통 reset이 필요하다. |
| 중간 | 절전 기상 버튼 처리 | 누름 이벤트는 기상 전용으로 반환하지만 이후 BtnB 해제/장기 누름 이벤트는 일반 처리된다. 기상 버튼을 놓기 전까지 소비하는 처리가 필요하다. |
| 중간 | 센서 초기화/오류 처리 | `M5.Mic.begin()`, I2C 설정 쓰기, 스프라이트 생성 등의 성공 여부를 확인하지 않는다. 진동 일부 수집 실패도 2개 이상이면 FFT로 진행한다. 장치 확인, 최소 유효 샘플 수, 오류 표시를 추가한다. |
| 중간 | 자력 재보정 | `sLastInstGauss`를 초기화하지 않아 이전 자력 출력이 새 기준선 보정 뒤 남는다. 기준선 확정 시 필터와 표시 상태를 초기화한다. |
| 중간 | 진동 샘플링 | 평균 샘플링 주파수 하나로 비균일 간격·중복 샘플 문제를 해결할 수 없다. ODR/data-ready/FIFO와 실제 타임스탬프 검증이 필요하다. |

추가 정리 대상: 사용하지 않는 `BatConfig` 전압 상수 및 UI 색상, 이전 16 kHz/2048 샘플 기준 주석, 과장된 절전 주석, `sMicEnabled`와 실제 초기화 성공 여부의 불일치.

## 6. 권장 개발 순서

1. 현재 환경의 빌드 결과와 실기기 기준 데이터를 확보한다. 알려진 주파수 입력, 무신호/충격음, USB 탈착, 버튼 반응 시간을 기록한다.
2. 녹음 완료 처리, 모드 전환/보정 취소, 검출·필터 reset을 먼저 정리한다.
3. 센서 존재/초기화/읽기 오류를 사용자에게 표시하고 로그에 샘플 수, 실제 Fs, peak, SNR, 검출 횟수를 남긴다.
4. 계측 요구에 맞게 회전당 주기 수와 자력 센서 계수를 명시하고 표준 장비와 비교한다.
5. 동작을 보존하며 `AppState`, `AudioAnalyzer`, `VibrationSampler`, `MagneticSensor`, `BatteryManager`, `DisplayView`로 분리한다. 우선 샘플 수집과 FFT 판정을 분리하면 하드웨어 없는 합성 신호 검증이 가능하다.
6. Arduino CLI 빌드 설정과 라이브러리 버전을 고정하고, 이후 CI에 컴파일을 추가한다.

수정 위치 안내: 대역·샘플 수·분석 주기는 `namespace Audio`, 감도는 `sensitivity*()`, 버튼은 `handleButtons()`, 자력 계수는 `processMagnetic()`, 화면은 `updateDisplay()`, 절전은 `updatePowerSaveState()`, 핀/초기화는 `setup()`이다. 샘플 수 변경은 FFT 객체, 배열 크기, 진동 zero padding, 잡음 추정 배열 용량을 함께 점검해야 한다.

## 7. 검증 환경과 범위

로컬 설치 확인: Arduino CLI, M5Stack 보드 패키지 3.3.9, M5Unified 0.2.25, M5GFX 0.2.33, arduinoFFT 2.0.4. 보드 FQBN: `m5stack:esp32:m5stack_sticks3`.

```sh
arduino-cli compile --fqbn m5stack:esp32:m5stack_sticks3 \
  --build-path /private/tmp/pano-checker-analysis-build \
  M5stickS3-motor-checker
```

컴파일 시도 결과: 설치된 `xtensa-esp32s3-elf-g++` 실행 단계에서 `bad CPU type in executable`로 실패했다. 소스의 컴파일 오류 여부를 판정한 결과가 아니며, 호스트에서 실행 가능한 툴체인 환경을 먼저 준비해야 한다. 장치 업로드, 실제 RPM/Gauss 정확도, 배터리 충전 전류·절전 전류 측정은 수행하지 않았다. 펌웨어 구현은 변경하지 않았다.
